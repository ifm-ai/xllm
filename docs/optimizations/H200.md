# H200 (sm_90a, 141 GB HBM3e) report

See [README.md](README.md) for the configuration fields and tests, and [H100.md](H100.md) for the Hopper kernels:
H200 is the same silicon, nothing was ported, every H100 item ran unchanged. One pass, 2026-10-25/26, on
8 x H200 SXM 141 GB (driver 610.57.04, NCCL 2.30.7, torch 2.14.1+cu130, xattn 1.1.1 with the patches in
`patches/`, DeepGEMM 2.8.2). The pass added the DeepGEMM backend of the fp8 GEMMs (`XLLM_FP8_DEEPGEMM=1`).

## TL;DR

- **The node was host-bound, not GPU-bound**: a KVM guest whose effective host clock switches between two speeds
  every few tens of seconds (~1.55x). The 0.9B / 4B steps were already near host-limited on H100; here the CPU no
  longer runs ahead of the GPU, FSDP2 issues each layer's all-gather late and step times are bimodal. Every number
  below is >= 30 steps per run, 2-3 alternating repeats, medians of the pooled steady steps. **On a bare-metal H200
  the host-bound rows would look different; re-check there before adopting the configuration changes.**
- The GPU itself is faster as expected: HBM 4.28 TB/s (H100 ~2.9), memory-bound kernels 1.26-1.44x per call.
- **What pays here: less host work per step.** `fsdp_layers_per_group` 4 / 6 / 2 and `reshard_after_forward=False`
  give **0.9B 444 ms, 4B 419 ms, 7.1B 536 ms** (H100 best 465 / 393-405 / 581-586); 2.42x / 1.82x / 2.02x against
  the baseline on this node.
- **7.1B at B1 L16384 fits without the FFN recompute** (118.8 GiB): 1048 ms, 15.4k tokens / s / GPU (OOM on H100).
- **DeepGEMM** (opt-in): 1.10-1.35x per fp8 GEMM, bitwise equal to cuBLASLt on the same operands; end to end
  7.1B -2 to -3%, 0.9B / 4B within the node's noise. Kept opt-in (see below).
- Did not work: swift SCA on 0.9B / 4B runs out of memory even at 141 GB; CUDA-graph blocks crash with EOS-packed
  data (xattn's BOS plan and swift's segment copy are host-side per-step state that gets frozen into the graph;
  without EOS the graph runs, 4B fp8 468-478 -> 431-454 ms).

## How to run fastest

All rows: `XLLM_FSDP_SYMM=1 NCCL_CTA_POLICY=2`, `fp8_gemm=True`, 8 GPUs, per-rank batches, 30-step runs x 2.

| preset | config on top | ms / step (median) | tokens / s / GPU | peak GiB |
|---|---|---|---|---|
| 0.9B B2 L16384 | `recompute_conv_qk=False`, `balance_dp_rows`, `reshard_after_forward=False`, **`fsdp_layers_per_group=4`**, bf16 reduce-scatter | 444 | 72.7k | 69 |
| 4B B1 L8192 | `recompute_conv_qk=False`, `reshard_after_forward=False`, **`fsdp_layers_per_group=6`** | 419 | 19.0k | 55 |
| 7.1B B1 L8192 (swift) | `XLLM_FP8_KEEP_X=1 XLLM_GEKKO_SAVE_RMX=1`, bf16 reduce-scatter, **`reshard_after_forward=False`, `fsdp_layers_per_group=2`, `recompute_conv_qk=False`, `XLLM_FP8_DEEPGEMM=1`** | 536 | 14.9k | 86 |
| 7.1B B1 L16384 (swift) | as the row above but `reshard_after_forward=True`, no FFN recompute | 1048 | 15.4k | 119 |

Baseline = torch AWM, CUB TSDN, torch elementwise, bf16 GEMMs, patched xattn. The baseline and the fp8 4B row are
slower than on H100 (host-heavy paths), the GPU-bound rows faster.

Per kernel (1 GPU, 0.9B B2 L16384, per call): conv + q-k prep forward 153 -> 106 us (1.44x), its backward 262 ->
210 us (1.26x), TSDN backward + residual 161 -> 117 us per layer (1.38x), attention gate + fp8 quantise 252 -> 241
us (1.05x), fp8 quantisation 2.6-2.7 -> 3.0-3.3 TB/s, fp8 GEMMs 1.0-1.24 -> 1.08-1.32 PF, xattn D256 backward
4025 -> 3908 us per layer (L2-bound). Memory-bound kernels gain 1.26-1.44x (HBM 1.47x), compute-bound ones about
nothing.

## Tests and parity

- All tests pass unchanged (test_fp8_sm90 38 incl. DeepGEMM, test_fp8_fsdp 5, test_fp8_gekko_block_sm90 6,
  test_fsdp_copy_in 6, the CuTe kernel tests, attention regressions 14, swift blocks 11).
- 60-step 1-GPU 0.9B, every optimized path vs every reference path: loss |diff| max 0.0004, grad norm within 0.15%.
- 8-GPU 30-step parity (same seeds), bf16 + symm vs every reference path: 4B loss |diff| max 0.0003, grad norm
  within 0.18%; 7.1B 0.0007 / 0.22%.
- 150-step soaks of the best configs vs bf16 + symm, 8 GPUs: 4B max |diff| 0.0045, last-10 losses equal; 7.1B
  <= 0.0042 through step 120, then late-plateau spikes in both runs (random-token data), last-10 10.3960 vs 10.3933;
  0.9B equal from step 52 on (`balance_dp_rows` reorders the rows rank 0 logs before that).

## Memory and host levers (8 GPUs, medians)

- `fsdp_layers_per_group` 2 / 4 / 6: 0.9B 450 / 444 / -, 4B 424 / 410-424 / 412, 7.1B 556 (2) / 552 (4) ms.
- `reshard_after_forward=False`: 4B fp8 514 / 591 -> 460 / 463 ms; part of every best row.
- No recompute at all (`recompute_conv_qk=False` + `XLLM_FP8_KEEP_X=1`): 7.1B best row (86 GiB); 4B 420 vs 424.
- bf16 reduce-scatter, `NCCL_PROTO=Simple`, NUMA pinning, explicit FSDP2 forward prefetch, HSDP (shard 4 or full
  replication), `XLLM_FP8_AG=1`: all within noise or slower on this node; FSDP over all 8 GPUs stays.

## DeepGEMM

- Microbenchmark, 30 GEMMs (fwd / dgrad / wgrad of 10 Gekko linears): 13.87 -> 11.77 ms, per GEMM 1.10-1.35x, one
  slower (4B q wgrad 131 -> 148 us). sm90 DeepGEMM takes only A 1 x 128 / B 128 x 128, so the weight gradient tiles
  X^T (`XLLM_FP8_SM90_WGRAD_TILE=x`, the default under DeepGEMM), and no residual epilogue with bf16 output (those
  GEMMs keep cuBLASLt).
- Integration: `fp8_sm90.mm` behind `XLLM_FP8_DEEPGEMM=1`, cuBLASLt default and fallback; `XLLM_FP8_DEEPGEMM_SMS`
  caps the SMs of its persistent kernels (no effect here; H100 measured 120 as best next to the overlapped
  reduce-scatter); `test_mm_deepgemm`.
- End to end: 7.1B 150-step soaks median 537 / 547 vs 554 / 555 ms; losses track cuBLAS within 0.0015 through step
  119, the late random-token spikes are higher in both DeepGEMM runs. Suggest a real-data loss comparison before
  making it a default.

## Open

- Re-measure the host-bound rows (0.9B, 4B, the layer-group settings) on a bare-metal H200.
- CUDA graphs with EOS-packed batches need padded / device-side varlen metadata in xattn (fixed-capacity cu_seqlens,
  max_seqlen = L) and a device-side swift segment layout: worth ~6% on 4B.
- fp8, symmetric collectives and DeepGEMM as defaults; the xattn patches upstream.
